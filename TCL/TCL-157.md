# Migration tool: convert the twelve existing sandpiper boards to Trail layout

Standalone Trail reads `.trail/config.json` and knows nothing about the `.sandpiper` layout. The boards on this machine are all in the old shape. A separate tool converts them.

## Settled design

`.sandpiper/docs/specs/trail-extraction-design.md`, "Migration tool" — marked **[settled]**.

A separate, **throwaway** CLI. It exists because we are currently Trail's only consumers; it is our migration, not a Trail feature.

**It does not live in the Trail repo.** Keeping it in sandpiper-ai is what lets it read `.sandpiper-tasks.json` and `.sandpiper/settings.json` — Sandpiper's formats — without Trail ever knowing they existed. That ownership boundary is the whole reason Trail gets to be compat-free.

**Interface:** `--tasks-dir`, plus an optional `--config-file`. It emits `./.trail/config.json` with the tasks-dir key pointed at the existing `./.sandpiper/tasks`.

**Tasks are not moved.** The point is to make old directories work in place, which keeps the migration reversible and decouples "adopt standalone Trail" from "reorganize every repo."

It must carry the whole `version_control` block forward, not just the tasks dir.

**Depends on TCL-163.** The tasks-dir config key does not exist yet; without it there is nothing to point at the old location with.

## Survey of the twelve boards (from the design record)

- **Eleven have a storage config**, so `--config-file` is the common case, not the rare one. The tool should *discover* the old config, with the flag as an override.
- **Five of twelve are partial** — missing `enabled`, `auto_push`, or both. Today's `mergeWithDefaults` is doing real work, so the old file is not a reliable source of every key. Trail's parser is now strict and total, so the tool must synthesize the complete shape.
- **`herdr` keeps its config in `.sandpiper/settings.json`**, not `.sandpiper-tasks.json`. Read both, or it silently flips from `enabled: false` to enabled.
- **Seven of eleven task dirs are live jj workspaces**: navigator, pi-claude-code-cli-provider, reinforced-guidance, sandpiper-ai, task-storage-spike, waymark, yaams.
- `reinforced-guidance` and `waymark` run `auto_commit: true`; everything else does not.

## The one outcome that can cause damage

From the design record, verbatim: defaults say `mode.branch: "@"` (inline), and **"handing a fresh 'you are inline' config to a real jj workspace is the one outcome here that can damage something rather than merely annoy."**

Seven of eleven boards are exactly that case. A tool that writes defaults instead of carrying the real `version_control` block forward will tell seven live jj workspaces they are inline. Treat this as the acceptance criterion the tool is built around, not as an edge case discovered during testing.

## Verification

Run against a *copy* of one separate-branch board, then run it again on the result. Assert resulting on-disk and VCS state — workspace still registered, branch intact, `task list` count unchanged, emitted config parses under Trail's strict total parser — not exit codes and not stdout. Three bugs found during the extraction (TCL-151, TCL-152, TCL-153) were all commands reporting intent instead of result, and all were invisible to tests asserting stdout.

Idempotence matters because re-running is the first thing a human reaches for. A dry-run mode belongs in scope: these are live boards with real history.

## Ordering constraint (settled, from the design record)

> The migration tool ships **before or with** the cutover. The moment Trail stops reading `.sandpiper/tasks`, every board on this machine is dark until migration runs against it.

Also fold in the toon 4.x index rewrite here (TCL-156) if indexes are rewritten at all — though note that with tasks staying in place, this migration may not need to touch `index.toon` at all, which would decouple the two entirely. Confirm before assuming.

## Proposed implementation plan for review

Planning only. Implementation and live adoption have not started. The current contract is Sandpiper's .sandpiper/docs/specs/trail-board-adoption.md. TCL-163 is COMPLETE; older notes above that say the task-directory setting does not exist are historical.

Goal: adopt one existing board in place by creating complete Trail v2 configuration. Keep task/history/index bytes, keys, directories, and effective VCS settings unchanged. Do not recreate or re-register task checkouts.

Proposed shape: a Bun/Commander tool under devtools/, with a thin CLI and a small adoption module. Data flow: read legacy source -> resolve effective values -> build and preflight a read-only plan -> report dry-run or exclusively create the canonical configuration. Existing legacy source files stay in place.

Proposed interface: --dir selects the project root, defaulting to the current directory; --tasks-dir explicitly selects the existing board; --config-file overrides legacy source discovery; --dry-run never writes. Output is <project-root>/.trail/config.json. No runtime VCS commands are needed.

Implementation order:
1. TCL-168: characterize legacy defaults/discovery and construct isolated fixtures.
2. TCL-169: pure conversion, path/configuration safety, and read-only dry-run planning.
3. TCL-170: thin CLI, exclusive writer, race/refusal handling, and repeat-run no-op behavior.
4. TCL-171: real Git/jj preservation, strict-parser verification, and old/new reader checks.

Each implementation step starts with failing tests. Dependencies express this order; parent and subtasks remain NOT STARTED while Doug reviews the plan.

Safety policy proposed for review: valid partial legacy files keep legacy effective defaults. Malformed JSON, unsupported shapes, mode/workspace contradictions, and conflicting or malformed Trail candidates refuse. A semantically equivalent valid configuration is an unchanged no-op. This is intentionally more conservative than the old reader's silent fallback for malformed input.

Verification uses state, not successful output: strict v2 parsing, unchanged data manifests, preserved workspace registrations/branches/commits, unchanged reader counts, and zero changes on dry-run/conflict/repeat. Test repositories must not contain pointers to live workspaces. CLI count checks use separate copies because reads can maintain indexes.

Boundaries: no new Trail legacy compatibility, index-format rewrite, data relocation, live twelve-board rollout, consumer assembly/cutover, dependency-method selection, publication, or TCL-167 fix. The twelve-board survey is dated input to recheck, not permission to migrate those boards. Production consumer strategy remains deferred; the standalone parser is an explicit test oracle only.
