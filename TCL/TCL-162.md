# Fold storage init into initialize

`storage init` still exists. The design record settles that it should not.

## Settled design

`.sandpiper/docs/specs/trail-extraction-design.md`, "`initialize`" — marked **[settled]**:

> New top-level command. `storage init` is removed and folded into it — the `storage` subcommand has poor discoverability and is confusing for most use cases.
>
> - Emits `./.trail/config.json` with **all defaults explicitly populated**.
> - **Never overwrites.** If a config already exists at any candidate path, `initialize` is a no-op consumer and fails loudly.

## What actually shipped

TCL-150 delivered `initializeCommand` and wired it into `index.ts`. It writes the config with defaults populated and refuses to overwrite. **But `storageInitCommand` is still registered** on `storageCommand` alongside `sync`, `push`, `pull`, and `migrate`. Both commands exist, which is the confusing surface the decision was meant to remove.

So this is not a deferred UX idea — it is a settled decision half-implemented. TCL-146's deferred list calls it "UX fix, not extraction," which is where this ticket's original LOW-urgency framing came from. The design record wins.

## Scope

- Fold VCS bootstrap into `initialize` and remove `storageInitCommand`.
- Note the interaction with **TCL-152**: the occupied-directory and empty-directory error behavior we just fixed lives inside `storage init`. That logic moves rather than dies, and its tests move with it. Do not treat the removal as license to drop those cases — they were reopened once already for reporting success while creating nothing.
- `initialize` currently touches no VCS at all. Folding bootstrap in gives it process-spawning behavior, which cuts against the seam boundary TCL-144 just finished establishing in the test suite. Route the bootstrap through the existing `VcsRunner` seam so the new path is unit-testable rather than integration-only.
- The never-overwrite check must consider **all** config candidates once TCL-161 lands, not just `.trail/config.json`.

Depends in practice on TCL-161 for the candidate-aware overwrite check.

## Autonomous-phase boundary — 2026-10-06

TCL-161 is implemented, so the shared candidate-aware overwrite safeguard is available. The bootstrap removal itself still needs a design clarification: `initialize` must emit default inline configuration and refuse every existing config, but the old `storage init` bootstraps only a preconfigured non-default branch or external repository. The current `storage sync/push/pull` commands do not bootstrap missing workspaces. Simply moving the old handler after writing defaults makes its non-default branches unreachable; deleting the old command would remove the only supported bootstrap workflow.

No new flags, config-input source, implicit initialization, or overwrite exception were invented while Doug was away. Left NOT STARTED pending the non-default bootstrap entry-point decision. The occupied/empty-directory safeguards and VcsRunner seam remain intact.

## Doug's decision — 2026-10-06

Use flags on `initialize` to control how storage is initialized, including non-default modes. An interactive terminal wizard is deferred. Emit a complete configuration, using explicit defaults for unspecified initialization options, and preserve the refusal to overwrite any existing configuration candidate. Strict parsing of existing files does not gain defaults. The authoritative design is updated. The non-default bootstrap entry-point decision is resolved; implementation is not yet claimed complete.
