# Slice 3: strict total config parse with exact version match

# Slice 3: strict total config parse with exact version match

Make config parsing total and versioned. This deletes inference rather than adding validation.

- **Delete `mergeWithDefaults`.** Every key must be present in the file. A missing key is a loud error naming the key. No fallbacks, no inferred defaults, no partial configs.
- **Add a `version` integer** to the config, and a baked-in expected version constant in Trail.
- **Exact match required.** File version must equal Trail's version. Higher OR lower is a loud error naming the fix, e.g. `config version 1, trail expects 2 — run trail migrate-config`.

Why exact rather than a max: accepting an older version means the binary must know which keys a past version lacked and supply them itself. That is precisely the inferred fallback being outlawed, just relocated into the parser. Ruled by Doug 2026-08-12.

Side effect worth preserving: with the version check running first, strictness about unknown keys is free and well-diagnosed — any config carrying keys Trail does not know will also carry a bumped version, so the version error fires first and says something useful instead of `unexpected key "auto_stash"`.

This should be LESS code than what it replaces. If the diff grows a validation layer, the shape is wrong — this is parse-don't-validate, so the parsed config type is total by construction and nothing downstream re-checks it.

Verification: `tsc --noEmit` clean, suite green, and tests covering: missing key rejected, version mismatch both directions rejected, well-formed config accepted.

## Reopened 2026-08-12 — `version_control` becomes a discriminated union (Doug)

Not a new ticket: this slice defined the config type, and this corrects the type it defined.

**Problem.** `enabled` is a flag beside the fields it governs, so contradictory configs are representable and accepted today:

```json
{"enabled": false, "mode": {"branch":"tasks","repo":"git@x:y.git"},
 "auto_commit": true, "auto_push": true}
```

VCS disabled, with a remote and both auto flags carrying meaningful-looking values. All noise, nothing rejects it. It also leaves `enabled` as a validator-style flag every consumer must remember to check before reading `auto_commit`.

**Shape:**

```ts
type TaskVersionControlConfig =
  | { enabled: false }
  | { enabled: true; mode: TaskStorageMode; auto_commit: boolean; auto_push: boolean };
```

"No VCS" is exactly `{"enabled": false}` — total, no nulls, no meaningless keys. Narrowing on the discriminant means the compiler enforces what discipline enforces today.

**Scope is narrower than it looks.** `DEFAULT_STORAGE_CONFIG` has `enabled: true`, so `initialize` writes the wide variant either way and needs no change. This is `storage-config.ts` (type + parser) plus consumer narrowing. TCL-150 is unaffected.

**Why now rather than later.** The `version` field exists, so a shape change after configs are in the wild costs a version bump plus `migrate-config` run against twelve repos. There are currently **zero** `.trail/config.json` files in existence. The cost only goes up.

And the migration tool is unwritten. herdr's real config is `{"version_control":{"enabled":false}}` and nothing else — under the current type, migration must invent `mode`/`auto_commit`/`auto_push` for it, writing meaningless data into a strict config we would then have to migrate away. Fixing the type first makes that tool's job smaller.

**Explicitly not doing:** collapsing `branch: "@"` (magic sentinel for inline mode) into an explicit variant. Same smell, much larger wire change, and nothing forces it the way the `enabled` case is forced.

**Gate:** `{"enabled":false}` alone accepted; `{"enabled":false, ...anything else}` rejected; `enabled:true` still requires all four; consumers narrow rather than re-check; tsc clean; suite green.
