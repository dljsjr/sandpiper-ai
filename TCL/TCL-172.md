# Packaging, distribution, and branding for standalone Trail

Doug has decided to host standalone Trail on GitHub and publish it on npm. Use GitHub Actions for CI/CD so npm releases can carry build provenance. This is a new standalone-project delivery task, not a reopening of the completed legacy CLI rebrand.

Status: backlog only. Do not start implementation, create remote resources, push, or publish as part of filing this ticket. Packaging can be planned independently of Sandpiper's overlapping refactor; it is not blocked on moving the TCL board.

## Scope

1. Review public branding and identity: project/CLI presentation, npm package name or scope, repository owner/name, and consistent package metadata, README, and licensing. Do not assume name availability.
2. Prepare the npm artifact: build output, executable entrypoint, supported runtime/dependency declarations, and intended package contents. Test the packed artifact from a clean installation without a Trail or Sandpiper source checkout.
3. Set up the GitHub home and GitHub Actions CI. Run the existing relevant tests, checks, build, and packaged-CLI smoke tests. Decide release triggers and approval gates before enabling publishing.
4. Design and test npm publication through GitHub Actions with verifiable build provenance. Verify current npm/GitHub authentication and provenance requirements before choosing the publishing mechanism. Do not commit credentials or rely on unexplained manual steps.
5. Write a first-publisher-friendly setup and release guide for Doug: npm account/package ownership, required permissions, authentication, versioning, release verification, and failure/recovery handling.

## Completion criteria

- Public identity, repository/package ownership, licensing, and metadata are reviewed and consistent.
- The package contains only intended files, installs cleanly, and runs representative CLI operations on a temporary board without a source checkout.
- GitHub Actions validates source and packaged behavior; the agreed release path cannot accidentally publish unreviewed pull-request or ordinary branch changes.
- The release procedure produces npm build provenance tied to the reviewed source and artifact, and explains how to verify it. Any first real publication requires Doug's explicit approval.
- Doug can follow the documented setup and release procedure without prior npm publishing experience. Plan and split implementation work when this ticket is picked up, not while filing it.

## Boundaries

No live-board adoption or relocation, Sandpiper bundled-Trail replacement, consumer cutover, unrelated CLI features, or Rust port. Public GitHub/npm distribution is decided; the exact branding, package identity, authentication method, release triggers, and Sandpiper consumption method are not. This ticket remains NOT STARTED until Doug chooses to begin it.
