# storage init silently no-ops on an existing empty tasks dir, reporting success with no VCS backing

`storage init` reports success and creates **no VCS backing at all** when the tasks directory already exists but is empty. Task files then accumulate in a plain, gitignored, untracked directory while every command says everything worked.

## Repro (no `initialize` involved — this predates it)

```sh
git init . && git commit --allow-empty -m init
mkdir -p .trail/tasks                     # the only bootstrap path before `initialize`
cat > .trail/config.json <<'JSON'
{"version":1,"version_control":{"enabled":true,"mode":{"branch":"trail-tasks"},
 "auto_commit":false,"auto_push":false}}
JSON
trail storage init
```

Output claims success:

```
Initialised separate-branch task storage at .../.trail/tasks
  Backend: git
  Branch:  trail-tasks
```

Reality:

| Check | Result |
|---|---|
| `git worktree list` | 1 entry — main only, no task worktree |
| `git branch -a --list trail-tasks` | branch was never created |
| `ls -A .trail/tasks` | empty |
| `.gitignore` | **`.trail/tasks/` was appended** |

`project create` afterwards "succeeds" and writes `PROJECT.md` into that gitignored, unbacked directory. jj backend behaves identically — `jj workspace list` shows only `default`.

Verified by sandpiper-rev on both backends, and independently reproduced with no `initialize` in the flow at all.

## Cause

`initSeparateBranch` and `initExternalRepo` (`src/core/storage-backend.ts:49,101`) use bare existence as an idempotence check:

```ts
if (existsSync(opts.clonePath)) return;
```

That treats "the directory is there" as "already initialized." It cannot distinguish a real worktree from an empty directory somebody just made.

**The codebase already has the sound version of this check**, in `migrate.ts:47`:

```ts
const isAlreadyWorktree = existsSync(join(workspacePath, '.git')) || existsSync(join(workspacePath, '.jj'));
```

`storage-backend.ts` has the weaker form of a check the same codebase gets right one module over.

## Provenance

Pre-existing. The guard is **byte-identical** in `sandpiper-ai/packages/trail/src/core/storage-backend.ts`, so it predates the standalone extraction. It was reachable before via the hand-`mkdir` bootstrap, which was the only documented way to create the tasks directory.

TCL-150's `initialize` did not introduce it — it promoted it from a path users stumbled into to **the default path**, since `initialize` now always creates the directory and only ever writes the inline default, making hand-editing `mode.branch` the sole on-ramp to separate-branch mode.

## Fix

Replace bare `existsSync` with a real initialized-check in both functions, matching `migrate.ts`'s shape: look for `.git` / `.jj` *inside* the target. Decide deliberately what an existing-but-empty directory should do — proceed and initialize into it is the obvious answer, since that is exactly the state `initialize` leaves behind.

A non-empty, non-worktree directory is a third case worth naming rather than assuming: failing loud is likely right, because silently initializing over existing task files is how the current bug got its teeth.

## Blocking

**Blocks TCL-146.** The cutover cannot close while its own default bootstrap journey silently produces an unbacked task directory. Needs regression coverage for `initialize` → mode switch → `storage init` on both backends; the current `initialize` tests only exercise inline mode.

## Resolution for all four states (sandpiper-rev, 2026-08-12)

One predicate over the marker, rather than reusing bare `existsSync` to answer two different questions:

| State | Behavior |
|---|---|
| `.git`/`.jj` marker present inside the target | already a real worktree — no-op. Today's correct idempotent case, unchanged. |
| No marker, directory **empty** | proceed and bootstrap. This is exactly what `initialize` leaves behind, and the case that is currently broken. |
| No marker, directory **non-empty** | **fail loud**, naming the path and what is in it. |

The third row is the one that matters for not repeating this bug: silently bootstrapping over unknown files is how the current defect earned its teeth, so "empty" must mean actually empty — not merely "no VCS marker."

Keep the distinction between *pre-existing* and *newly-default* in any writeup of this. It is the difference between "always been broken, low blast radius" and "now the first thing every new user hits."

## Reopened 2026-08-12 — the fail-loud message points at data loss

Found in the TCL-146 acceptance run, not by any slice-level test, because it only appears in the full journey.

Natural sequence: `initialize` → create projects and tasks → decide you want separate-branch storage → edit `mode.branch` → `storage init`. Result:

```
Error: Cannot initialize separate-branch storage: .../.trail/tasks already exists,
is not a git/jj worktree, and is not empty (contains: .gitignore, ACME, index.toon).
Move or remove its contents before running `storage init`.
```

**The refusal is correct** — that is the fail-loud third state working as designed, and it does not clobber anything. **The guidance is not.** `storage migrate` exists precisely for this case and handles it correctly (verified: real worktree created, task files preserved, `task list` intact afterwards). Telling the user to "move or remove its contents" points them at deleting the task tree when a safe migration path is one command away.

The contents named in that error — `.gitignore`, `index.toon`, project directories — are **Trail's own task tree**, not the unknown files the fail-loud rule was written to protect. Those are distinguishable.

Fix: when the occupying contents look like a Trail task tree, say so and name `storage migrate`. Keep the current wording for genuinely unknown contents, which is the case the rule exists for. Do not weaken the refusal itself.

Not blocking TCL-146: the cutover works and the journey completes via the correct command. Filed because guidance that reads as "delete your tasks" can cost real work.
