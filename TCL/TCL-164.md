# task update fails on relationship fields written after updated_at

`task update --depends-on/--blocked-by/--related` fails with `Cannot update frontmatter field "updated_at" because its YAML form is non-round-trippable by Trail's surgical writer.` when the relationship array is the last frontmatter field, after `updated_at`. `task create` with relationships writes them in that order, so every task created with `--depends-on` hits this on its first relationship change.

Cause: `replaceArrayField()` in `src/core/mutate.ts` removes the existing array with `^<field>:.*(?:\n  - .+)*`, which leaves an empty line between `updated_at` and the closing `---`. The comment there assumes `updated_at` is always the last field. `touchUpdatedAt()` then runs `assertRoundTrippableFieldForm()`, and `findFrontmatterFieldForm()` counts that empty line as a continuation line of `updated_at`, so the check throws.

Repro (`applyFieldUpdates(content, { dependsOn: ['A-2'] })`):
- `depends_on` after `updated_at`: throws.
- `depends_on` before `updated_at`: ok.

Live hit: 2026-10-06, `task update AGENT-295 --depends-on AGENT-293` and the same on AGENT-296. Worked around by editing the files directly. `~/git/trail` has the same `replaceArrayField()`.

## Inbox report supplied by Doug (2026-10-06)

The September report below describes the same array-removal defect, so it is preserved here rather than filed as a duplicate. Both symptoms originate in replaceArrayField: removing the field leaves its terminating newline behind. If the array was after updated_at, the leftover blank line is treated as an updated_at continuation and the update throws. If the array was before updated_at, the update succeeds but leaves a blank frontmatter line.

Verified on standalone Trail in /tmp/trail-writer-repro.5WZ78B. Added initialize for the neutral layout and created TST-3 before updating TST-2, so all relationship targets existed. Updating the trailing related list failed with the reported updated_at error. Inserting a previously absent related list did NOT insert a blank line in this version; removing that list DID leave a blank line after created_at. No live boards were used. No production code changed.

### Original inbox report

# Trail: two frontmatter writer bugs with `related` (2026-09-25)

Found while filing tasks in another project. Reproduced in an empty scratch project with the bundled `trail` CLI.

## 1. `task update --related` fails when `related:` is the last frontmatter field

Steps:

```sh
trail project create TST --name Test --description repro --when-to-read never
trail task create -p TST -t base
trail task create -p TST -t "with related" --related TST-1
trail task update TST-2 --related TST-1,TST-3
```

Result: `Error: Cannot update frontmatter field "updated_at" because its YAML form is non-round-trippable by Trail's surgical writer.`

`task create --related` writes `related:` (a block list) after `updated_at`, as the last field before `---`. Other updates of the same task work (`--priority`, `--status`). Only an update of `related` fails, and the error names `updated_at`.

Real cases: two tasks in another project.

## 2. Inserting a block list leaves a blank line in the frontmatter

Steps:

```sh
trail task create -p TST -t "no related"
trail task update TST-3 --related TST-1     # inserts related: before updated_at, plus a blank line after created_at
trail task update TST-3 --related ""        # removes the list, keeps the blank line
```

The blank line stays after later writes. A task in another project has one from a `depends_on` list that was removed on 2026-09-24.
