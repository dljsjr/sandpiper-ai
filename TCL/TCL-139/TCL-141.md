# Exempt WONTFIX from check 2 (blocker resolution)

Resolved the open design question from TCL-139: check 2 (blocker resolution) now mirrors the existing NEEDS-REVIEW-before-DONE rule's treatment of WONTFIX as an abandon-from-anywhere resolution -- no longer requires blockers to be resolved when finalizing with WONTFIX. DONE still requires all blockers COMPLETE+DONE, unchanged.

Doug explicitly decided NOT to extend the same exemption to check 1a (children-complete-before-finalize), after a real asymmetry was identified: check 1b (parent COMPLETE blocks active children) only looks at parent status, not resolution, so exempting WONTFIX from check 1a would let a parent go COMPLETE with open children, which check 1b would then immediately flag as a fresh violation on those same children. The two checks looked structurally identical but weren't safe to treat the same way.

Implementation: added resolution to UpdateFieldGuardInputs; enforceUpdateFieldGuards computes resultingResolution the same way it already computes resultingStatus (fields.resolution ?? current.resolution) and skips check 2 when resultingStatus is COMPLETE and resultingResolution is WONTFIX. Also updated diffGuardRelevantFields (task-cmd-helpers.ts) to diff resolution, so an interactive nvim WONTFIX also gets the exemption, not just the flag-based path.

Verified: 4 new tests (WONTFIX bypasses check 2 without --force; DONE still blocked; check 1a still blocks WONTFIX with open subtasks, confirming the asymmetry decision; interactive-path resolution diffing). 430/431 tests pass (1 known pre-existing jj/git flake). tsc/biome clean. End-to-end CLI smoke test confirms WONTFIX succeeds without --force despite an unresolved blocker, and DONE still correctly blocks.
