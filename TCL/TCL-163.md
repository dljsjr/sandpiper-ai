# Make the task tree location configurable so configs can point at existing storage

Trail cannot be told where the task tree lives. `tasksDirPath(rootDir)` is a pure function of the root and the hardcoded `TASKS_DIR_SEGMENTS = ['.trail', 'tasks']`, and `TaskStorageConfig` carries only `version` and `version_control`. This is settled design that has not been implemented.

## Settled design

`.sandpiper/docs/specs/trail-extraction-design.md`, "Config content" — marked **[settled]**:

> Default tasks dir is `./.trail/tasks`. Overriding it is a key in the config file.

It is load-bearing for the whole extraction, not an enhancement. The migration tool's settled behavior depends on it entirely: it "emits `./.trail/config.json` with the tasks-dir key pointed at the existing `./.sandpiper/tasks`. **Tasks are not moved** — the point is to make old directories work in place, which keeps the migration reversible and decouples 'adopt standalone Trail' from 'reorganize every repo'." Seven of the eleven configured boards keep their task tree in a live jj workspace; relocating those is precisely what this key exists to avoid.

The design record also names the concept this replaces: the extraction's central finding is that Trail's only coupling to Sandpiper was **16 hardcoded path literals** all spelling one unnamed concept — *the task tree lives at `<root>/.sandpiper/tasks`*. TCL-147 introduced the constant. This ticket is the other half: making the value configurable rather than merely named.

## Shape

- Add the task-tree location key to `TaskStorageConfig`. The **config file** location stays governed by TCL-161's candidate list — that is the bootstrap anchor and cannot itself be config-driven.
- Make `tasksDirPath` config-derived, defaulting to `.trail/tasks` when unset. Six non-test call sites: `migrate.ts`, `auto-commit.ts`, `storage-cmd.ts` (×3), `initialize-cmd.ts`, plus `resolveTasksDir` in `commands/helpers.ts`.
- Bump `CONFIG_VERSION` to 2. TCL-149 made the parse version-exact, so a new key is a new version by construction. Cost here is nil: the migration generates every config from scratch anyway.
- Resolve the value against the **project root**, consistent with `--dir`. Note the design record marks path resolution **[recommended]**, not settled — "agreed in substance, not explicitly ratified." Confirm before relying on it.
- Reject `..` escapes and decide relative-vs-absolute. Relative-to-root is the honest default.

## This forces TCL-151's correct fix rather than its cheap one

Today `resolveTasksDir(basePath?)` takes no config, and `emitMutationResult` resolves config *after* the mutation is written and reported — that ordering is TCL-151, where a malformed config yields a written task, a success line, then a crash.

Once the task tree's location comes from config, **config must resolve before anything can touch the task tree at all.** The ordering stops being a convention that can drift and becomes a data dependency. That is TCL-151 fix direction (a) — recorded there as "correct and expensive," and TCL-138's rank-1 cleanup candidate — arriving as a consequence of this design rather than as separate work.

Sequencing consequence: doing this first makes TCL-151 largely fall out. Doing TCL-151's cheap fix (b) first means writing a workaround this ticket then deletes.

## Doug's decision — 2026-10-06

Ratified support for both absolute and relative task-directory paths. Relative paths resolve against the project root (`--dir` or cwd), not the directory containing the configuration file. Absolute paths are used as given. The authoritative extraction design now marks path resolution settled. The prior decision blocker is resolved; implementation is not yet claimed complete.

## Implementation and verification — 2026-10-06

Added required non-empty string `tasks_dir` to the strict schema and bumped CONFIG_VERSION to 2. The emitted default is `.trail/tasks`; existing configuration never receives an inferred value. All command/store/VCS paths now derive from this value. Relative paths resolve against project root, absolute paths can point outside it, and relative `..` escapes refuse before task I/O.

Configured task creation/indexing was demonstrated red before implementation. Other red-to-green cases cover empty paths, relative escapes, storage bootstrap/gitignore selection, auto-commit directory, sync/push/pull directory, and migration leaving the default tree untouched. Coverage also includes all config candidate locations, absolute external directories, required/type-checked values, root-only ignores, and literal glob/space escaping. Root gitignore entries are omitted for outside-root stores.

All 549 tests / 34 files pass; typecheck and build pass; all four public JSON examples parse under version 2. Real Git ignores the literal special-character task directory but not a wildcard-shaped sibling. Built CLI reads/mutates an existing configured store in place without creating `.trail/tasks`, and preserves the original task bytes. Scratch probes: `/tmp/trail-path-ignore.XYfesm` and `/tmp/trail-configured-store` with generated suffix recorded in session output.

Documentation updated to actual version-2 behavior. No live boards or consumers were changed. Left NEEDS REVIEW for Doug.
