# Flaky jj test cleanup: rm -rf intermittently fails in afterEach

The jj backend integration tests in storage-cmd.test.ts use execSync('rm -rf "${rootDir}"') in afterEach to clean up jj workspace directories (Node's rmSync fails on macOS with jj's .jj/ structure). This cleanup intermittently fails with 'Command failed: rm -rf ...' when run in the full test suite (parallel execution), though tests pass individually.

Likely cause: jj's workspace background processes or file locks haven't released by the time afterEach runs when other test files are executing concurrently.

Options:
1. Add a short delay before cleanup
2. Use vitest's --no-file-parallelism for this test file
3. Wrap rm -rf in a retry loop
4. Accept the flakiness (it only affects cleanup, not test assertions)

## Current standalone investigation

Investigated on macOS 27.0, Node v24.22.0, Bun 1.4.3, jj 0.46.0. No current failure reproduced and no source/test-infrastructure cleanup change made.

The original jj cases moved from storage-cmd.test.ts to src/core/storage-backend.integration.test.ts. Current storage-cmd.test.ts uses a fake VCS runner and rmSync; the real jj backend cases retain shell rm teardown.

Evidence:
- Baseline 586 tests / 37 files passes; after TCL-167, 589 / 37 pass.
- Ten additional full parallel-suite runs all pass (589 tests each).
- Thirty additional storage-backend integration runs all pass.
- A Node-based real-jj probe creates and removes 100 separate-workspace fixtures: 50 with Node rmSync, 50 with /bin/rm -rf, all pass without retries or sleeps. .jj/repo in those workspaces is a regular file on current jj, not a symlink.
- Test JJ_CONFIG isolates the user configuration. Effective fsmonitor.backend is none, and fsmonitor.watchman.register-snapshot-trigger is false. Watchman is installed but not enabled by the current test fixture. No host config/live repository changed.

Recovered the original April 3 failure from session history: shell rm returned failure for storage-init-jj-test-XIMCYy; 310/311 tests passed. That saved result contains no errno, rm stderr, or exit status beyond the failed command. It proves the historical flake but does not establish its cause. Differences in jj/runtime/macOS and test config can matter; none is proven as the historical cause. No assumption that background processes, locks, or symlinks caused it.

Artifacts: /tmp/trail-tcl110-tests.EVo1DP (10 full and 30 focused logs); /tmp/trail-tcl110-cleanup.mjs (Node runner); /tmp/trail-tcl110-config.T2dxXm (isolated config probe). Direct cleanup result: nodeRmSync=50, shellRm=50, workspaceRepoPointer=regular file. Await Doug's decision whether to retire this historical unreproduced report or retain it for a future failing log. No claim that the bug is fixed.
