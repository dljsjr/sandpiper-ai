# Bracket in a task title wedges the board, and index update cannot repair it

A task title containing `[` wedges the entire board: the title round-trips into `index.toon` fine, but every subsequent CLI invocation fails to parse it — including `index update`, which is the repair tool.

## Repro (verified 2026-08-12 against ~/git/trail tip)

```sh
trail task create -p TST -t "foo bar[0] (= baz): quux"   # succeeds
trail task list                                          # Error: Line 7: Unexpected content "(= baz)" between bracket segment and colon
trail index update                                       # same error — cannot self-repair
```

The offending line is a properly double-quoted scalar in key-value position:

```
    title: "foo bar[0] (= baz): quux"
```

The decoder opens a bracket segment on `[0]` despite it being inside quotes. Recovery required hand-patching the line to a bracket-free title, after which `index update` reconciled cleanly.

## Cause: upstream, and fixed in a PATCH release we never took

Not Trail's code. `@toon-format/toon` is pinned at **2.3.0**. The fix shipped in **2.3.1** on 2026-07-16 — fifteen days before this wedged a 245-task board — and its release notes name the defect outright:

- `decode: Treat quoted spans as opaque in line classification`
- `decode: Slice key-value rest at key token end offset`
- `Harden encode and decode against prototype pollution`

Verified by direct probe of the failing index text:

| Version | decode |
|---|---|
| 2.3.0 | throws `Unexpected content ... between bracket segment and colon` |
| 2.3.1 | decodes correctly |
| 4.1.1 | decodes correctly |

The failure is position-dependent, which is why it went unnoticed: in a **tabular array row** (`[1]{key,title}:`) even 2.3.0 handles the same string fine. Only the nested-map key-value form Trail's index actually uses breaks.

## Fix: bump to 2.3.1. Do NOT bump to 4.x as part of this.

**2.3.0 → 2.3.1 changes nothing but the bug.** Encode output is byte-identical (verified on a multi-task index with uniform and ragged entries plus a deep single-key chain). No index churn, no migration, no breaking changes.

End-to-end verified 2026-08-12 against a copy of Trail tip with 2.3.1 installed: `task create` with the bracket title, then `task list`, then `index update` — all succeed.

**2.3.0 → 4.1.1 rewrites the index format.** v4 introduced a keyed tabular form for objects of uniform objects, which is exactly what Trail's `tasks` map is:

```
# 2.3.x                          # 4.1.1
tasks:                           tasks[2:]{key,project,title,status,kind,priority}:
  "TST-1":                         "TST-1": TST-1,TST,one,NOT STARTED,TASK,MEDIUM
    key: TST-1                     "TST-2": TST-2,TST,two,COMPLETE,BUG,HIGH
    project: TST
    ...
```

Ragged entries stay nested, so it is a mixed rewrite rather than a uniform one. Every board's `index.toon` would be rewritten on the first `index update` after the bump. v4.0.0 also removed key folding and path expansion; Trail does not appear to rely on either, but that was not exhaustively checked.

That trade may well be worth taking later — the tabular form is markedly smaller, which matters for an index that ships into agent context — but it is a format migration across twelve boards and deserves its own ticket and its own decision. It is not a bug fix.

**Correction to an earlier revision of this ticket:** it claimed 2.3.0 and 4.1.1 encode identically and recommended bumping straight to 4.1.1. That was measured with a single-entry `tasks` map, which does not trigger the keyed tabular form and therefore could not distinguish the two versions. The test was not discriminating; the conclusion drawn from it was wrong.

## Second fix, independent of the bump

`index update` should tolerate — or skip and report — unparseable index lines rather than dying on them, because it is the repair tool. A tracker whose repair command is disabled by the damage it repairs has no recovery path. This holds regardless of the parser fix: an index written by an older Trail, a different tool, or a hand-edit can still be unparseable, and today that state is terminal.

`packages/capability-autotoon` pins 2.3.0 as well and should be checked in the same pass.

## Resolution, 2026-08-12

**Landed in ~/git/trail as `wprskpsx`: bumped to 4.1.1, not 2.3.1.** Doug's call — Trail is its own only consumer, the format change is acceptable breakage, and a board migration tool is already being written, so the rewrite rides along with a migration that has to happen anyway rather than becoming its own event.

Verified: wedge repro clean end-to-end (create with a bracket title, then `task list`, then `index update`), 487/487 green, tsc clean, no Trail source changes needed.

**Sequencing is now tracked in TCL-156 and is not optional.** 4.x reads 2.3.x output; 2.3.x cannot read 4.x output. Every consumer — including the bundled tasks skill script, which is a build artifact rather than a dependency declaration — must be on 4.x before any 4.x Trail writes a real board.

Still open here: `index update` should survive an unparseable index rather than dying on it. That is independent of any version bump — a hand-edit or an older writer can still produce one, and today that state is terminal for the board.

## Repair implementation and verification — 2026-10-06

Committed `lvqmxwto` / `153279a3`. Recursive number scanning preserves archived subtasks and moved tombstone IDs when rebuilding an unreadable index, without following symlink directories.

Independent read-only review passed: decoder-only recovery and archived-number preservation were confirmed. Optional diagnostic/options-object suggestions were not added to this bug fix.
