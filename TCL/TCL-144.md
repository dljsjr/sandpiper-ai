# Rewrite Trail VCS tests to not require real git/jj (command-runner seam + thin integration set)

Rewrite Trail's VCS-touching tests so the default test suite requires no real git/jj binaries or host VCS state at all, per Doug's direction (2026-08-07): "Ideally, we'd rewrite those tests entirely to not require those resources at all."

Current state: packages/trail storage-backend/auto-commit/storage-cmd/migrate/vcs tests spawn real git and jj processes. That is why the GIT_CONFIG_GLOBAL/GIT_CONFIG_SYSTEM=/dev/null + JJ_CONFIG fixture neutralization exists on the root test:vitest script (2026-08-06, after real 1Password signing prompts fired on the developer's machine) - the neutralization makes real-VCS spawning safe, but the ideal is tests that never need it.

Shape (test pyramid, avoiding the tautology trap this project keeps catching): (1) the majority of cases move to unit tests against an injected command-runner seam - trail already funnels VCS calls through small helpers (e.g. run(command, args, cwd) in storage-backend.ts), so the seam is natural: assert on the exact command sequences trail ISSUES and its handling of scripted outputs/failures, without executing anything. This tests trail's logic, not a mock of git's behavior. (2) A deliberately thin set of true integration tests KEEPS real git/jj coverage (the reality-check layer - things like the auto_push no-upstream product bug TCL-143 would not be visible to a command-fake), explicitly marked/isolated, running under the existing env neutralization, possibly opt-in or reduced-frequency. (3) The root-script GIT_CONFIG/JJ_CONFIG neutralization STAYS until this lands, and stays even after for the residual integration set.

Not part of the AGENT-249 integration-harness lane (different resources, different problem): this is about the UNIT suite not requiring machine VCS, while the harness lane is about spawned-pi tests not requiring providers/credentials. Same principle, two applications.

## Acceptance evidence, 2026-08-12 (Roux) — this looks DONE

Re-reviewed against `~/git/trail` tip. All three parts of the specified shape are present:

**(1) Command-runner seam, with the unit tests on it.** `storage-backend.ts` owns `VcsRunner`, a module-level `vcsRunner`, and `setVcsRunner`/`resetVcsRunner` test-only seams. Four unit files drive it: `storage-backend.test.ts` (31 tests), `storage-cmd.test.ts`, `auto-commit.test.ts`, `migrate.test.ts`. They assert on the exact command sequences Trail issues and its handling of scripted outputs and failures.

**(2) Thin, explicitly marked integration set.** Real git/jj now lives in exactly three files, all named `*.integration.test.ts`: `storage-backend.integration.test.ts`, `auto-commit.integration.test.ts`, `storage-init-after-initialize.integration.test.ts`. Nothing outside them spawns git or jj — verified by searching every test file for `execFileSync`/`execSync`/`spawnSync`/`Bun.spawn`. The three non-integration files that matched spawn `bun <CLI_PATH>` (end-to-end CLI invocation), not a VCS.

**(3) Neutralization retained, and improved.** The `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM=/dev/null` and `JJ_CONFIG` fixture setup moved out of a root-script env prefix into `vitest.setup.ts`, where it is package-local and carries a comment explaining the 1Password signing-prompt incident that motivated it. That is the ticket's requirement met in a better form than specified.

Suite is green: 487 tests, 32 files, under `bun run test`.

Moving to NEEDS REVIEW rather than closing it — the work landed across the extraction and nobody ever walked it back against this ticket's acceptance criteria. If the reviewer agrees the three parts above satisfy the shape, close it DONE.

Caveat on the assessment: I did not evaluate whether the seam's unit tests fell into the tautology trap this ticket explicitly warns about (asserting on a mock of git's behavior rather than on Trail's logic).
