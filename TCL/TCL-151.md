# Mutation with malformed config writes the task, prints success, then crashes

A mutation with a malformed `.trail/config.json` **completes the write, prints success, then crashes** — leaving the user unable to tell what state they are in, and silently skipping auto-commit.

## Repro

`.trail/config.json` with a wrong-typed leaf, e.g. `"enabled": "no"`:

```
$ trail task create -p TST -t x
Created TST-1: x
  File: .../.trail/tasks/TST/TST-1.md
Error: config.version_control is missing required key "enabled".
$ echo $?
1
```

The task file **is** on disk. Exit is 1. Auto-commit did not run and nothing says so.

Coverage across the surface is uneven:

| Command | Behavior with a malformed config |
|---|---|
| `task list` (any read) | no error, exit 0 — read paths never resolve config |
| `storage sync` / `storage init` | error up front, exit 1, nothing done — correct |
| `task create` / any mutation | writes, prints success, then throws, exit 1 |

## Cause

`emitMutationResult` in `src/commands/helpers.ts` orders the work:

```
mutate → updateIndex(...) → resolveStorageConfig(rootDir) → autoCommitIfEnabled(...)
```

The config parse happens *after* the mutation has already been written and reported.

## Provenance — this predates the extraction

Verified by sandpiper-rev against `sandpiper-ai/packages/trail` pre-extraction: the ordering is **byte-identical** there. The original `parseJson` / `mergeWithDefaults` swallowed malformed input and returned defaults, so it could never throw — the ordering had no observable consequence.

TCL-149 (strict total config parse) did not introduce this. It is mechanically the **first change that could ever surface it**. Strictness exposing a latent ordering bug is strictness working.

## Why HIGH rather than someday

It is now genuinely reachable. A hand-edit typo that used to silently "work" now visibly breaks on the next mutation, and 11 of the 12 boards on this machine have hand-written configs. It also reaches sandpiper-ai once that repo vendors the extracted Trail and inherits the strict parser.

## Two directions — do not default to the first

**(a) Reorder `emitMutationResult`** so config resolves before the write. This is the honest fix, and it is also the write-path / audited-projection boundary — TCL-138's rank-1 cleanup candidate. Not a casual cut, and explicitly off the standalone-cutover critical path.

**(b) Handle it where it already fails.** Catch the config failure at the existing call site and fold it into the output the command already prints — `saved, not auto-committed: <reason>` — instead of an uncaught throw after a success line. Narrower, honest about what happened, and does not touch the write boundary.

(b) is cheap and may be sufficient. (a) is correct and expensive. Recording both deliberately so the expensive option is not the only one written down.

Found during TCL-146 slice review, 2026-08-12. Not a blocker for the standalone extraction.

## Implementation and verification — 2026-10-06

Committed `nvtnrmsz` / `70a3e1cf`. The shared task-tree path entry point now strictly resolves configuration before a command can read or write the tree. This prevents the reported save/success-output/late-config-error sequence without masking errors after saving or introducing config defaults. No TCL-163 path semantics were selected.

The original create regression failed red with `Created AGENT-3` before the error. Six mutation regressions now cover create/update/pickup/complete/move/archive, including unchanged task bytes and no new index or archive. Real scratch CLI task and project creation both refused malformed configuration before creating files/directories. Reproduction retained at `/tmp/trail-config-preflight.DiulER`.

Full suite: 524 tests / 33 files pass; `bun run check` passes. Optional independent read-only review requested. Left NEEDS REVIEW for Doug.

## Independent review — 2026-10-06

Read-only review passed. Confirmed every task/project/index command uses the shared preflight; storage commands already resolve configuration before accessing task paths; initialize correctly refuses existing configuration without parsing it. The regression assertions cover files/index state, not only exit status. No wrapper abstraction was added for the discarded parse result; TCL-163 will eventually consume it when task-directory semantics are ratified.
